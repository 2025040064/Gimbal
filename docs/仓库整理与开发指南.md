## 软件版本组织

独立实验阶段按 1–8 的编号顺序保留。每个阶段内部的 `Core/`、`Drivers/`、`HARDWARE/`、`MDK-ARM/` 与 `LED.ioc` 保持原位置。第 8 阶段最接近当前综合功能，但“最新”不等于功能已测试通过。

各工程之间存在大量重复的 STM32 HAL / CMSIS 等供应商文件；目前每个阶段作为独立可打开的 Keil 工程保存，**不能盲目删除重复文件或只留最后一个阶段**。

## 发现的维护问题与建议处理

1. **根目录 README 原来仅有一句介绍**：已补充定位、文件导航及现阶段技术边界。
2. **仓库跟踪了大量 Keil 构建生成物**：抽查发现 `.o`、`.d`、`.crf`、`.axf`、`.hex`、`.map` 等；新加 `.gitignore` 仅对将来新产生的文件生效，不会清除已提交文件。保留 HEX 的发布需要另行规范。
3. **没有统一整机采购说明**：已把 Word 里 13 类物资与仓库代码结合整理，并保留 PCB 电子 BOM 的独立入口。
4. **`HARDWARE/MORTOR` 拼写存在历史遗留**：需待 Keil 引用检查后才能改名。
5. **CubeMX/手写初始化有差异**：例如 `LED.ioc` 配置未完整覆盖手写的 USART3、ADC、TIM2，生成新代码前先确认。
6. **闭环术语需谨慎**：现有 `stabilizer.c` 是目标像素误差追踪，不可混淆为 MPU6050 惯性云台稳定闭环。
7. **K230 的 `Display.ST7701` 配置**：若采购无屏幕板卡，应核对具体硬件和显示初始化方式。

## 文档更新纪律

- 每增加/更换器件，更新 `docs/BOM_物资采购清单.md` 的规格、数量、来源及验证状态。
- 每产生新软件阶段，注明依赖芯片、编译环境、外设配置和测试结果，**禁止未经确认覆盖其他阶段**。
- 每修改结构或 PCB，记录文件格式、版本号及机械配合尺寸；需有可复现的原理图和 BOM。
- 删除编译产物、做目录迁移、整合重复 HAL 库前，务必先备份，并在独立分支验证构建。

**本文仅实施仓库结构的文档级整理，没有宣称构建或实物功能已验证。**
